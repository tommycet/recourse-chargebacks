The Problem

The x402 specification defines a 4-step payment flow: request → payment required → authorization → settlement. No dispute mechanism. No delivery verification. No chargeback. Once settled, the payment is final.

How It Works
01 ESCROW

Funds Held On-Chain

Payment is locked in a smart contract before any work begins. The seller can't touch the funds until the buyer confirms delivery — or the arbiter resolves a dispute.

02 EVIDENCE

Cryptographic Proof

Every request and response is hashed with keccak256 and committed on-chain at creation time. The evidence bundle creates a tamper-proof audit trail for any dispute.

03 ARBITER

AI-Powered Resolution

When a dispute is raised, an on-chain arbiter reviews the evidence bundle and issues a binding refund or payout — deterministic, machine-speed, no intermediaries.

Architecture
Multi-Agent Pipeline

Four independent agents, one onchain verdict

Every dispute flows through four specialized agents that verify independently before KeeperHub executes. No single agent can force a settlement — each phase gates the next.

┌────────────────────┐ ┌────────────────────┐ ┌────────────────────┐ ┌────────────────────┐ │ PHASE 1 │ │ PHASE 2 │ │ PHASE 3 │ │ PHASE 4 │ │ Evidence Verifier │───▶│ AI Arbiter │───▶│ Policy Agent │───▶│ KeeperHub │ │ │ │ │ │ │ │ │ │ keccak256 proofs │ │ LLM + rule fallback│ │ Refund / payout │ │ MCP + Direct API │ │ source/target sig │ │ evidence review │ │ matching policy │ │ onchain execution │ │ delivery check │ │ binary verdict │ │ gas-aware routing │ │ audit trail logged │ └────────────────────┘ └────────────────────┘ └────────────────────┘ └────────────────────┘ │ │ │ │ ▼ ▼ ▼ ▼ fail → dispute refund / pay retry on gas spike Blockscout tx ↗ evidence bundle → verdict → onchain settle

Reliability built in: Phase 4 retries on gas spikes with exponential backoff and records every action in the KeeperHub audit trail (trigger → simulation → submitted tx → gas → outcome → timestamp).
