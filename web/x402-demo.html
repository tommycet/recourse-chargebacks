x402 + Chargeback Protection

The x402 spec processes payments before delivery is verified — once funds leave the buyer, there's no dispute mechanism. Recourse intercepts the 402 flow and routes payments through on-chain escrow instead.

The Problem

x402 has no chargebacks — and that's by design

The x402 specification treats irreversibility as a feature. But no serious buyer routes value through rails with zero recourse. Card networks learned this in 1974.

⚠ x402 Protocol Spec, §2
"Payment is final — once settled, there is no dispute mechanism, no delivery verification, no chargeback. The payment is final."
— x402 Protocol Specification v2, Core Payment Flow
Standard vs Recourse

Two paths after the 402 response

The same HTTP 402 triggers fundamentally different behavior depending on whether Recourse is in the loop.

✗ Standard x402 — No Protection

Direct payment → no recourse

// Standard x402: buyer pays directly POST /resource HTTP/1.1 Content-Type: application/json X-Payment: {"x402-version": 1, "payment": {"signature": "0x..."}} → 200 OK + resource payload // ⚠ Payment is FINAL. // ❌ No escrow // ❌ No delivery verification // ❌ No dispute mechanism // ❌ If seller delivers nothing → funds gone
✓ Recourse x402 — Escrow Protected

Escrowed payment → full protection

// Recourse: buyer agent intercepts 402 POST /resource HTTP/1.1 Content-Type: application/json X-Payment: {"escrowId": 42, "amount": "1000000", "taskId": "0xabcd..."} → 200 OK + resource payload // ✅ Funds locked in RecourseEscrow.sol // ✅ Evidence bundle committed on-chain // ✅ confirmDelivery → release to seller // ✅ raiseDispute → AI arbiter resolves
Architecture

Recourse as x402 Proxy

The Recourse client sits between the buyer agent and the seller. It intercepts 402 responses, creates an escrow, and submits the escrow proof instead of a direct payment.

The Flow

HTTP 402 → Escrow → Delivery → Settlement

Each step is backed by on-chain state. The buyer agent never loses custody of funds until delivery is confirmed.

⚡ Interception Point Step 02 → Step 03

Recourse intercepts between the 402 response and the payment authorization

In standard x402, the buyer receives the 402 Payment Required response and sends a payment signature directly to the seller — funds leave the buyer's wallet immediately, with no recourse. Recourse breaks that flow. Between receiving the 402 and authorizing payment, Recourse creates an on-chain escrow instead. USDC is locked in a smart contract, not sent to the seller. Funds move only after delivery is confirmed — or after the 4-agent pipeline resolves a dispute.

✗ Standard: 402 Response → Buyer signs payment → Seller gets funds
✓ Recourse: 402 Response → Escrow created → Seller gets escrow proof → Delivery confirmed → Escrow releases

⚡ Intercept
03

⚡ Recourse intercepts: creates escrow instead of authorizing payment

WAITING
This is the interception point. Instead of signing a payment and sending funds directly to the seller (standard x402), the Recourse client creates a RecourseEscrow on Sepolia. USDC is approved and locked in the contract — not sent to the seller. The buyer retains custody until delivery is confirmed.
RecourseClient.payWithRecourse() → USDC.approve(escrowAddr, 1000000) → Escrow.createEscrow( buyer, seller, 1000000, taskId, evidenceBundleHash ) → EscrowCreated(id=42) // on-chain event
04

Submit escrow proof to seller

WAITING
The buyer re-submits the request with an escrow proof (ID + amount + taskId) instead of a direct payment signature. Seller sees the escrow is funded and delivers the resource.
POST /api/summarize-article HTTP/1.1 Content-Type: application/json X-Payment: { "escrowId": 42, "amount": "1000000", "taskId": "0xabcd...ef01", "proof": "0x7f3a...c8b2" } Body: {"task": "summarize-article-2026"} → 200 OK + summarized content
05

Delivery confirmed — or dispute raised

WAITING
If delivery succeeds: confirmDelivery(42) releases USDC to seller. If it fails or times out: raiseDispute(42) freezes the escrow and triggers the 4-agent arbiter pipeline.
// Happy path — delivery confirmed Escrow.confirmDelivery(42, evidenceHash) // → USDC released to seller // Failure path — dispute raised Escrow.raiseDispute(42, disputeEvidenceHash) // → Escrow frozen // → 4-agent pipeline: Verifier → Arbiter → Policy → KeeperHub
06

Settlement on Sepolia

WAITING
KeeperHub executes the final settlement tx on-chain. The entire flow — from 402 to resolution — is logged in the KeeperHub audit trail with gas estimation and retry logic.
// KeeperHub executes on Sepolia Escrow.resolveDispute(42, true, buyerAddr) // → USDC refunded to buyer // → TX: 0x6ad71f82...056afa0 // → Block: #11,374,381 // → Audit: 7z0t2yr9ecczhx0tfgad6

Evidence Bundle

Cryptographic proof of the full transaction

Every x402 payment through Recourse generates a signed evidence bundle — request, response, delivery status — all hashed into a single bytes32 commitment stored on-chain.

STEP 1

Build

Hash the request URL, response body, delivery status, and timestamps into a structured evidence bundle using keccak256.

STEP 2

Commit

The bundle hash is committed on-chain when the escrow is created. Both buyer and seller can verify the hash matches the original payloads.

STEP 3

Verify

When a dispute is raised, the evidence verifier checks the on-chain hash against the reconstructed bundle. Tamper-proof: no one can alter evidence after commitment.

// EvidenceBundleV2 — stored as keccak256 on-chain interface EvidenceBundleV2 { version: uint8 // 1 taskId: bytes32 // keccak256(task description) buyerAddr: address // 0x8c0c5c07...ea535a2 sellerAddr: address // 0x7532A98C...D3acCe amount: uint256 // 1000000 (1 USDC) requestHash: bytes32 // keccak256(url ‖ taskDesc) responseHash: bytes32 // keccak256(responseBody) deliveryStatus: uint8 // 0=failed, 1=delivered timestamp: uint256 // epoch seconds signerPubKey: bytes32 // compressed secp256k1 X coord } // bundleHash = keccak256(abi.encode(bundle)) // Stored on-chain in createEscrow() // Verified on-chain in verifyBundle()
